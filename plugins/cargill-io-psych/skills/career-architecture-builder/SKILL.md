# Career Architecture Builder

Build a coherent job architecture: a family/sub-family/level structure with a
consistent leveling logic, dual career ladders, and level descriptors distinct
enough to actually place a role. Output an **Excel leveling matrix** and a
**Word career-framework narrative**.

## Why This Skill Exists

Career frameworks fail in one of two ways: levels that read the same (so
placement becomes politics) or factors applied inconsistently across functions
(so "Level 4" in Finance ≠ "Level 4" in Supply Chain, breaking pay equity and
analytics). A defensible architecture applies the **same leveling factors** —
scope, complexity, autonomy/decision-rights, and impact — across every family,
writes **observably distinct** descriptors per level, and provides **dual
ladders** so deep experts advance without managing people. This skill enforces
that consistency and distinctness so the framework holds up under comp review and
employee scrutiny.

## Process

### Step 1 — Set the structure
Confirm the hierarchy: **job family → sub-family → level**. Decide the number of
levels and confirm a **dual ladder** (IC/expert track + people-manager track)
with **equivalent levels** (e.g. IC5 ≈ M3). See `references/leveling.md`.

### Step 2 — Fix the leveling factors
Use the same four factors across all families: **Scope**, **Complexity**,
**Autonomy / decision-rights**, **Impact** (add Influence/Communication if the
org's framework uses it). These are the columns of the matrix. Do not let a
family invent its own factors.

### Step 3 — Write level descriptors per factor
For each level × factor cell, write a short descriptor of what that factor looks
like at that level. Enforce **adjacent-level distinctness**: no two adjacent
levels may read the same on a factor. Use the progression language in
`references/leveling.md` (e.g. scope: task → project → program → function →
enterprise).

### Step 4 — Differentiate the dual ladder
At equivalent levels, describe how the IC/expert and manager tracks differ in
*how* they create impact (depth/technical authority vs people/operational
leadership) while holding *level of* impact equivalent. This keeps the tracks
genuinely parallel for pay and status.

### Step 5 — Add progression criteria
For each level boundary, state what must be demonstrably true to move up
(evidence, not tenure). Keep criteria observable and factor-aligned.

### Step 6 — Place example roles & generate deliverables
Map any supplied roles onto the matrix to sanity-check distinctness, then produce
the Excel matrix and Word narrative per `references/deliverable-spec.md`. Append
the disclaimer.

## Deliverables

1. **Excel — Leveling Matrix.** Rows = levels (both ladders), columns = the four
   factors (+ summary). Cells = level × factor descriptors. A `Role Placement`
   tab maps example roles to levels with rationale; a `Distinctness Check` flags
   any adjacent cells that read too similarly.
2. **Word — Career Framework Narrative.** Structure, factors, level summaries,
   dual-ladder logic, progression criteria, role-placement examples, governance
   notes, disclaimer.

## Standard Disclaimer

> Draft career architecture for review by HR, Total Rewards, and legal/comp
> partners. Level placement, pay-band alignment, and FLSA/exemption implications
> must be validated before adoption; this framework is a structure, not a
> compensation or classification decision.

## Hard rules

- **Same four factors across every family.** Consistency is the whole point.
- **Adjacent levels must be observably distinct** on each factor — run the
  distinctness check.
- **Dual ladders hold level-of-impact equivalent** while differing on how impact
  is created.
- Progression is **evidence-based**, never tenure-based.
